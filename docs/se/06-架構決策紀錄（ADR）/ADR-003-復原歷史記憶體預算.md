# ADR-003：復原歷史以記憶體預算（位元組）限制，而非只限步數
- 狀態：採納（1.3.0）
- 背景：iPadOS Safari 在分頁記憶體過高時會直接重新載入頁面（Jetsam），對使用者等於作品不見。1.0 的歷史只以 120 步限制；每一步保存整份文件快照（cel 緩衝區共用、不可變），大畫布×多影格時 120 步可能保留數百 MB 的舊版 cel。
- 決定：
  1. 每個歷史項目在 push 時計算 `cost`：`bOnly` = 只存在於 before（復原需要的舊版）的緩衝區位元組，`aOnly` = 只存在於 after（重做需要的新版）的位元組，另加兩份 meta JSON 大小。文件目前使用中的緩衝區不計入（屬於文件本身）。
  2. 歷史佔用 = Σ undo.bOnly + Σ redo.aOnly（線性歷史下精確，O(步數) 計算）。
  3. 預算：iOS／iPadOS 96 MB、`navigator.deviceMemory ≤ 4` 的裝置 128 MB、其他 320 MB；步數上限提高為 200；永遠保留最新 10 步。
  4. 每次 commit（本機、AI、遠端同步 `pushHistory()`）後執行 `enforceHistoryBudget()`，從最舊步驟移除；第一次因預算移除時以提示告知，歷史面板顯示「N 步 · 復原記憶體 X / Y MB · 已移除最舊 K 步」。
- 替代方案：差異（diff）壓縮、把舊步驟分頁到 IndexedDB——效益較高但複雜，列為未來評估；只降低步數——對小畫布過度保守、對大畫布仍不夠。
- 後果：大型文件可復原的步數變少（以提示與面板說明）；單元測試含 256×256×10 圖層×50 影格的 commit 效能守門（< 40 ms/次）。
